# exp_01 design — common semantic DAG

## 1. Semantic contract

Each rank owns a generated outbound buffer and a local inbox. In the two-rank
anchor, rank `r` transfers every logical record to rank `1-r`. The consumer on
the destination may read record `i` only after the selected method's publication
edge makes that record or its enclosing group eligible.

For epoch `e`, source rank `s`, destination rank `d`, record `i`, and 64-bit
word `j`, the payload is generated by one fixed integer mixer:

```text
v = mix64(e, s, d, i, j)
```

The payload is never constant across adjacent epochs. Every backend consumes
the same generated work list and produces the same two-part digest:

```text
digest_sum ^= mix64(v, i, j)
digest_add += v * odd_constant(i, j)  (mod 2^64)
```

The pair is supplemented by deterministic elementwise samples from the first,
middle, last, and pseudo-random records. No floating-point arithmetic appears
in the transport-equivalent correctness path.

## 2. Buffers and ownership

| buffer | shape | owner | lifetime |
|---|---|---|---|
| `outbound[q]` | `[records][record_bytes]` | source rank | producer writes epoch `e` |
| `inbox[q][source]` | `[records][record_bytes]` | destination rank | transport writes epoch `e` |
| `ready[q][source][group]` | `epoch32` | destination-visible | publisher writes after payload |
| `consumed[q][source][group]` | `epoch32` | source-visible | consumer returns reuse credit |
| `digest[q]` | two `u64` plus sample status | destination rank | consumer result |
| `timestamps[q]` | producer/transport/consumer begin/end | local rank | one write/site/epoch |
| `errors[q]` | bitset and first mismatch | local rank | all-rank reduced |

`q = e mod depth`, with `depth ∈ {1,2}` for Stage 0. A slot is writable only
after every required `consumed[q] >= e-depth` observation. The first epoch uses
nonzero epoch value `1`; a zero-initialized ready cell can never satisfy it.

## 3. Exact Stage-0 counts

At 64 KiB records and 64 MiB/rank:

- records/rank: `64 MiB / 64 KiB = 1024`
- 64-bit words/record: `64 KiB / 8 = 8192`
- semantic payload/rank/direction: `64 MiB`
- semantic payload for the bidirectional two-rank round: `128 MiB`
- source/destination groups at destination-epoch granularity: one per source
- payload publication count: method-specific and recorded, never inferred
- consumer digest input count: exactly `1024 × 8192` words/rank

The fixed-volume family uses `records = 64 MiB / record_bytes`. The
fixed-count family requests 4096 records and reduces geometrically only when
the two payload buffers plus workspace would exceed 50% HBM.

## 4. Direction-equivalent method mappings

### CU push

The source rank reads `outbound[q][i]`, writes the peer's
`inbox[q][source][i]`, drains payload writes, then publishes readiness on the
destination. The destination polls and acquires before loading the inbox.

### CU pull

The destination rank waits for source-production readiness, reads the source's
`outbound[q][i]`, writes its own inbox, drains local writes, and publishes local
consumer readiness. The same local consumer reads the same inbox layout as the
push arm. Bidirectional rounds prevent initiator placement from changing total
work.

### Host copy path

The source process submits copies from materialized outbound storage to the
same destination inbox layout. Descriptor submission, queueing, completion,
and ordered publication are timed. It is labeled `host_copy_path` until each
point has executor evidence.

### MORI paths

MORI P2P and MORI SDMA must call the same pinned nonblocking-put API with the
same grouping, process model, memory type, completion operation, and
publication. Only an independently verified transport selector may differ.
If that pair cannot be produced, both remain complete-path methods and no
hardware-engine main effect is reported.

## 5. Publication and consumption

Every valid arm implements:

```text
producer complete
  -> payload operation(s)
  -> direction-appropriate release/drain
  -> ready epoch publish
  -> ready observe + acquire
  -> dependent digest/sample loads
  -> consumed epoch publish
```

Fine and grouped readiness are deferred to Stage 4. Stage 0 initially uses one
destination epoch per `(source,destination)` so transport direction/engine is
not confounded with publication count.

## 6. Timing

Primary time is a host/coordinator synchronized global window:

```text
all ranks ready
epoch release
method-specific producer + transport + dependent consumer
all ranks complete
```

Per-rank GPU clocks are used only for local component spans. Cross-GPU clock
subtraction is forbidden. Each record stores:

- host global start/end and launch skew
- local producer, transport, and consumer begin/end
- `Tp`, `Tm`, `Tcons`, `Tserial`, `Tideal`, and `Tjoint`
- enqueue time and post-final-operation completion time
- rank-max minus rank-median completion tail

HIP-event/device-span agreement is pre-registered at 5% or 2 µs, whichever is
larger, for spans above 20 µs. A disagreement blocks timing publication.

## 7. Correctness gates

Before timing each point:

1. generate a new epoch-dependent outbound payload
2. poison the entire inbox and digest output
3. run one eager epoch
4. verify two-part digest, deterministic samples, zero poison, and generations
5. all-reduce errors across ranks
6. run each applicable negative control and prove its expected failure bit
7. reinitialize all protocol state
8. complete 600 epochs with no timeout, mismatch, poison, or generation error

Timeouts are classified as deadlock, watchdog, or censored-slow outcomes and
are not cleared and retried as noise.

## 8. Negative-control expectations

| control | mutation | expected detector |
|---|---|---|
| dropped publication | skip final source/destination ready | bounded-poll timeout |
| early publication | publish before payload drain | digest/sample or poison failure; if it never fails across the stress schedule, the control is invalid |
| redirected destination | offset one record into the wrong inbox partition | digest and sampled mismatch |
| dropped credit | suppress one `consumed` update | next slot-reuse bounded-poll timeout |
| early reuse | overwrite `q` before retirement | generation or digest mismatch |
| unordered SDMA signal | payload and signal use un-ordered queues | digest/sample/poison failure; required before executor-labeled SDMA timing |

## 9. Fairness strata

Results compare methods only within identical:

- process topology and rank/GPU binding
- memory allocation/registration/cacheability stratum
- payload values, work list, inbox layout, and consumer
- payload volume and readiness granularity
- warm/cold-cache protocol
- timing bracket and launch count accounting

If one engine requires a different memory stratum, run the crossed
`method × memory_type` control and report the interaction. Do not attribute it
solely to the engine.

## 10. Reused Distributed-HipKittens primitives

- peer projection: `translate_peer`, `peer_offset`
- CU push/pull: packet helpers in `packet.cuh`
- release/acquire: `thread_release`, `thread_acquire`
- readiness: epoch publication and bounded observation in `completion.cuh`
- slot lifetime: reusable-slot wait and retirement in `lifetime.cuh`

The explicit outstanding-operation-depth parameter is added at the benchmark
call site first. If the repeated call sequence is stable and wins, promote it
additively into `packet.cuh`; existing callers remain bit-identical.
